# A whole-library random Drill draws one Domain, weighted by what's studied there

A random Drill can be started at any time, scoped to the whole library, one Subject, or hand-picked Concepts. A Subject sits in one Domain, and hand-picked Concepts must all share one, so those scopes settle the Drill's Domain themselves. Picks that span Domains are refused, not split. The whole library is the exception, since a Drill never crosses Domains (ADR 0001). So an unscoped random Drill first draws a Domain. It picks one studied Concept at random and takes that Concept's Domain. It then drills every studied Concept in that Domain. A Domain therefore comes up in proportion to how much of the studied library it holds. A Domain with one studied Concept is drilled less often than one with fifty, but it is still drilled.

Once the Domain and candidate Concepts are known, a random Drill goes through the same composition, generation and scheduling as a due Drill. "Random" describes where the candidates come from, not how they're chosen. Composition still ranks them weakest and soonest-due first, so a random Drill over a large Domain asks about the Concepts that most need it. It does not ask about a uniform sample. Answering a random Drill advances each Concept's review schedule exactly as a due Drill would (ADR 0006), even though none of those Concepts was due.

We considered asking for a Domain before a whole-library Drill, one button per Domain like the due-list. That puts a choice in front of the default the ticket says should need none, and with one Domain it's a pointless click. We also considered drawing Domains uniformly. That would drill a Domain with a single studied Concept as often as the main one. This is easy to revisit: the draw is a few lines in `startRandomDrill`, and nothing stored depends on how it was made.
