# A Question links to its Concepts through a join table, and Concepts it asks about can't be deleted from under it

A scenario Question combines two or more Concepts, so the single `questions.concept_id` column became a `question_concepts` join table (question, Concept, position). The rule for how many Concepts a Question has — exactly one for recall and flashcard, two or more distinct ones for a scenario — lives in application code (`assertQuestionConcepts`), not the database. It is checked when Questions are created and again whenever they're read back, where a Question whose links no longer fit raises `QuestionIntegrityError` instead of being skipped or passed on. A Drill silently missing a Question would misreport its progress and summary, so it's better for it to fail loudly.

A Drill's Questions and their links are written by one database function, `create_questions`, so they land in a single transaction and a Drill is still all-or-nothing now that it spans two tables. That function handles persistence only. It checks the input's shape but makes no decisions about which Concepts may combine.

The link's foreign key to `concepts` does not cascade. Deleting a Concept that Questions still ask about would leave those Questions with too few Concepts, so the database refuses it. The check is deferred to commit, so a delete that removes every such Question as well still goes through. Deleting a Domain removes its Drills and their Questions along with its Concepts. One-off Questions asked outside a Drill belong to no Drill, so they block the delete until they are removed first. Nothing in the app deletes Domains, Subjects or Concepts yet. Whichever ticket adds deletion has to decide what happens to those Questions and their Attempts in application code.

We considered a `concept_ids uuid[]` column, which keeps Question writes to one table but can't enforce that each id is a real Concept. We considered inserting Questions and links separately and deleting the Questions if the second insert failed, which avoids a database function but leaves a window where Questions exist without Concepts. We also considered cascading Concept deletes to the links and pruning Questions left short. That would quietly discard a scenario's Attempts, or change what it tests, when one of its Concepts is deleted.

This is hard to reverse because the backfill drops `questions.concept_id`, and every Question from now on is stored only through its links.
